# yuniview

コンテナのログ・メトリクス・分散トレースを一か所で調査するセルフホスト型アプリです。独立した Go agent が収集し、Bun/Hono と PostgreSQL が取り込み・検索・モニター評価を担当します。React の画面と API は同じサーバーから配信します。

## 起動

```sh
docker compose up -d --build
```

http://localhost:3000 を開きます。初回はサービスが空なので、[agent の手順](agent/README.md) に沿って送信元を登録し、計測対象からデータを送ります。既存の Compose 環境では起動時の migration がスキーマを適用し、中央サーバーが過去のバッチを順次索引化します。PostgreSQL のデータは named volume に残ります。

本番の管理画面 https://yuniview.yuniruyuni.net は Cloudflare Tunnel 経由で公開し、Cloudflare Access の Owner ポリシーで指定した Google アカウントに許可します。アプリは画面と操作 API の両方で Access の署名、発行元、有効期限、アプリ固有の Audience を検証します。本番の環境変数は yunirun.jsonc にあります。手元の Compose は loopback 上で開発用の `YUNIVIEW_ADMIN_AUTH=local` を使います。

agent の送信先は、手元ではポート 3001、本番の同一ホストでは `/run/yuniview-ingest/http.sock` です。取り込みには送信元ごとの資格が必要です。

## 画面

PC から使う管理画面です。どの画面も「データ → 期間 → 条件 → 分け方 → 値」という同じクエリで動き、フィールドの名前・単位・説明はフィールド辞書から取ります。

| 画面 | 操作 |
| --- | --- |
| ホーム | サービスごとの要求数・失敗率・p95・最終受信。下に「ホーム」ダッシュボードを表示し、「ホームを編集」で自由に組み替えられます |
| サービス | 1サービスの要求数・失敗率・p95、リビジョンごとの比較、ルート別の件数と最も遅い要求 |
| 探索 | データ（リクエスト・スパン・ログ・イベント・メトリクス）を選んで行を見ます。フィールドを開くと値ごとの件数が出て、押すとその値で絞り込みます。行を押すと全属性・トレース・前後のログを表示し、「パネルにする」で同じ条件のままパネルを作れます |
| ダッシュボード | フィールドを棚にドラッグしてパネルを組み立て、折れ線・棒・面・ピボット表・数値で表示します。ダッシュボード全体に効く条件も持てます |
| モニター | パネル編集の画面に「判定」を足して作ります。プレビューに閾値の線を引き、過去7日で判定した場合の発報回数を確かめてから保存できます |
| 設定 | フィールド辞書。送信元が付けた名前・説明・単位・数値の種類（瞬間値か累積値か）・既定の集計を一覧し、利用者が上書きできます |

上部の期間と条件（フィルター）はホーム・サービス・探索で共通です。条件は URL に残るので、そのまま共有できます。

### フィールド辞書

フィールドの表示名・説明・単位は、まず送信元が付けたものを使います。OpenTelemetry のメトリクスは `description`・`unit`・種類（gauge か、単調増加の cumulative sum か）を受信時に保存します。日次集合は `daily_set` の payload に `label`・`description` を付けられます。yuniview の agent が集める資源（メモリ・CPU）と訪問の日次集合には、agent のプロトコルとして名前と単位が付きます。画面の「名前と単位を設定」や設定画面で上書きした値は、送信元の値より優先されます。消すと送信元の値に戻ります。

### 値の組み立て

パネルの値は「集計方法 × フィールド」です。フィールドを縦軸にドラッグすると、辞書の既定の集計（なければ型に合った集計）で追加されます。数値には合計・平均・最小・最大・p50・p95・p99、累積値のメトリクスには「増加率」（1秒あたりの増え方）、失敗には「割合」、属性には「種類数」が使えます。種類数のチップに別の属性を落とすと組の種類数になります。値のメニューの「合計する単位」で、たとえばスロットごとに1分ずつ平均してから合計できます（複数のコンテナのメモリ合計など）。

## Coding Agent から設定する

本番の Streamable HTTP MCP エンドポイントは `https://yuniview.yuniruyuni.net/mcp` です。管理画面と同じ Cloudflare Access の Owner セッションを使います。ローカル Compose の接続先は `http://127.0.0.1:3000/mcp` です。

Codex CLI では、次の設定を `~/.codex/config.toml` に追加します。

```toml
[mcp_servers.yuniview]
url = "https://yuniview.yuniruyuni.net/mcp"
env_http_headers = { "cf-access-token" = "YUNIVIEW_ACCESS_TOKEN" }
```

管理者の端末で次のコマンドを実行し、ブラウザーで Owner アカウントにログインします。トークンは環境変数からヘッダーに渡されます。セッションが切れたら同じ手順で再接続します。

```sh
cloudflared access login https://yuniview.yuniruyuni.net >/dev/null &&
YUNIVIEW_ACCESS_TOKEN="$(cloudflared access token --app=https://yuniview.yuniruyuni.net)" codex
```

たとえば「web の直近60分のメモリ使用量をプレビューし、blue・green 別のダッシュボードとして保存して」と依頼できます。サービス名や指標名は `list_telemetry`、フィールドの名前・単位・種類は `list_fields`、既存設定と版は `list_configuration`、集計の試行は `preview_panel` で取得します。`save_dashboard` と `save_monitor` には完全な定義と `expectedVersion` を渡します。新規作成時は新しい UUID と null を使い、更新時は取得した版を指定します。競合時は設定を読み直し、変更を反映してください。

ダッシュボードで「編集モード」を押すと、表示中のグラフや表のタイトルをつかみ、その場で配置順を変えられます。「全幅」でカードを1行に広げ、「設定」で個別のワークシートに移動します。「＋ パネル追加」をドラッグするとその位置に挿入できます。行と列には複数のフィールドを配置できます。たとえば行にサービス・スロット、列にワークロード・指標名を置くと、その順に階層化した表になります。棚をクリックするか、フォーカスして Enter を押すと、検索して項目を追加できます。行・列に置いたメトリクスをクリックすると、その指標の集計を変更できます。表示形式とフィルターはワークシート全体に適用されます。画面上部の期間はダッシュボードの全パネルで共通です。直近の期間またはカレンダーの日付範囲を選択でき、その期間を含むURLを共有できます。棚内のフィールドはドラッグまたは Alt＋左右矢印で並べ替えられます。サービスやスロット、受信済みのログ・スパン・メトリクス属性を置いて集計でき、メトリクスを同じ棚に追加すると指標名で比較できます。候補に重ねてプレビューし、離して下書きに反映します。Esc でドラッグを取り消し、ダッシュボードから直接開いたパネルは「セーブ」で保存します。配置編集中は「セーブ」でパネルの変更を下書きに反映し、配置画面の「保存」でまとめて公開します。「キャンセル」で今回のパネル編集を破棄します。

ワークシートの行・列には属性、時刻、指標を配置できます。配置した時刻をクリックし、区間単位（1秒〜1日）とタイムゾーン（JST・UTC）を個別に選べます。値のチップをクリックすると集計方法と表示単位を選べます。表示単位は同じ系統の単位どうし（B・KiB・MiB・GiB、ns〜s、µs/s・コア・%）で換算します。「1日・JST」は日本の午前0時、「1日・UTC」はUTCの午前0時で区切ります。日次集合は「1日・JST」を使います。右端のフィールド一覧の上でデータと表示形式を選びます。その左隣にフィルター専用のドロップ欄と各割り当て先が一段ずつ並び、折れ線なら横軸・縦軸・色・線種・太さ・点の形、棒や積み上げ面なら横軸・縦軸・色が並びます。ピボット表には行・列、数値と集計表には値・分類を使います。スタイル欄に属性をドロップすると、その属性で系列を分けて描画し、右側の凡例に反映します。凡例の「スタイルを編集」で、色・線種などの「全項目」と属性値ごとの個別指定を一覧で編集できます。表示形式「自動」では、指標の反対側に時刻（1秒〜1日）を置くと折れ線、カテゴリを置くと棒グラフになります。

フィルター棚に属性を置くと、その場で観測値を複数選択したり、数値・日時の上下限を指定できます。「本文・名前」を置くと、ログの本文やスパン・メトリクスの名前を部分一致で検索できます（大文字・小文字を区別しません）。同じ属性の選択値は OR、異なる属性の条件は AND で組み合わせます。

グラフにカーソルを合わせると、ガイド線の位置にある各系列の観測値が表示されます。グラフにフォーカスして矢印キーでも位置を選べます。

「エリアグラフ」は同じ単位の系列を積み上げ、累積値を折れ線で結びます。各系列の寄与は半透明の帯で表示します。欠測をまたぐ線は描きません。

「表示形式 → 積み上げ面」では、同じ単位の全系列を時刻またはカテゴリごとに積み上げます。各帯にポインタを合わせると系列の値と観測合計が表示されます。観測していない区間は空白です。

## モニターと保持期間

中央サーバーが毎分、直前に完了した分までの指定窓を評価します。グループを指定したモニターは、最低件数を満たす系列のうち閾値を超えたものがあれば発報します。該当系列がゼロなら欠測の設定に従います。状態変化は PostgreSQL に保存され、複数サーバーの評価は行ロックで調整されます。

- `MONITOR_WEBHOOK_URL` を設定して中央サーバーを起動すると、モニター単位で Webhook 通知を選択できます。通知には状態、時刻、値、イベント ID が入り、送信失敗時は再試行します。受信側は Idempotency-Key で重複排除できます。
- `TELEMETRY_RETENTION_DAYS` は受信日を基準にした保持日数です。1〜3650 を指定すると古いバッチと索引を段階的に削除します。既定の 0 は自動削除を無効にします。
- `TELEMETRY_PAYLOAD_DAYS` は、届いた元データ（バッチの payload）を行に展開した後も残す日数です。既定は 7 で、過ぎると元データだけを段階的に削除します。行とバッチは残ります。0 は削除しません。

## 開発・検証

client、server、e2e は template 由来の Bun workspaces です。共有する画面モデルは shared、スキーマは schema、収集プロセスは agent にあります。

```sh
bun install --frozen-lockfile
bun run check:type
bun run check:lint
bun run check:test
bun run build
(cd e2e && bun x playwright install chromium)
bin/test-console.sh
bin/test-agent.sh
```

統合テストは一時 PostgreSQL コンテナを起動します。console のテストはビルド済みアプリを Chromium で操作し、トレースとログの関連付け、保存済みダッシュボード、モニターの発報・復旧・欠測、Webhook 配送を検証します。

[サーバーのアーキテクチャ](docs/architecture.md) · [プロダクト設計と今後の yunirun 統合](docs/product-design.md)

パネルのデータを「日次集合」にし、「ログイン利用者」（`visit.account`）または「訪問ブラウザー」（`visit.browser`）を縦軸に置くと、日付（JST）×サービスの利用者数を表示できます。別の集合も同じように扱えます。ログやスパンでは、属性を縦軸の値の枠に落とすと重複を除いた種類数になります。ログインアプリは検証済みのアカウント、公開アプリはその日の同一ブラウザを1件とします。ブラウザデータを消した場合や別端末を使った場合は別件です。agent は Unix ソケットで受けた ID を、スロット間で共有するサービス専用鍵・日付・種別で HMAC 化してから配送します。中央はスロットや再送をまたいで重複を除き、30日を過ぎた記録を削除します。再配置時には `deploy/yunirun/attach` のアプリ名に `:browser` または `:account` を指定します。

日次集合は、日付とサービス内でのみ比較可能な匿名識別子向けです。認証済みの agent ingest に `signal: "daily_set"`、`payload: {"day":"2026-11-22","field":"cart.active","digest":"…"}` を送ると、集合名がフィールド候補に現れます。`digest` には64桁の小文字16進ダイジェストを指定します。空文字は計測済みの0件を記録します。`label` と `description` を付けると、フィールド辞書の表示名と説明になります。期間全体で同一 ID を数える場合は、ログ・スパンの属性を種類数として値に置き、表示を「数値」に設定します。

データを「イベント」にして「実行回数」を合計すると、受信したイベントの件数を加算します。探索の「イベント」で詳細と属性を確認でき、ワークシートの行・列・色・フィルターに `attr:event.name` などを置けます。HTTP の要求はデータ「リクエスト」で数えます。アプリ固有の操作は [agent のアプリケーションイベント](agent/README.md#アプリケーションイベント)から送信できます。日次集合とイベント履歴を個人単位で結合するキーは保存しません。
